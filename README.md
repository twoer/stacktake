# Stacktake

本机资产清点台账。看看自己机器上到底堆了什么。

除「Git 仓库 / 工具链缓存 / 编辑器与 AI 工具」三组的清理入口外**全程只读**；它也不接触任何凭据、不读文件内容、不代跑用户级命令、不监听端口。

## 装

目前**没有预编译安装包**——0.1.0 还没发布，Releases 页是空的。从源码构建：

```bash
npm install
npm run tauri build
```

产物在 `src-tauri/target/release/bundle/`。未签名构建在 macOS 首次打开会提示无法验证开发者，右键 → 打开。

## 它清点什么

> 下文所有体积与条目数是**作者机器 2026-10-20 的一次扫描快照**，用来说明界面上会看到什么，不是你机器上的预期值。界面与本文的「GB」都是 GiB（2³⁰）——同一份数据的读数比 Finder 的十进制 GB **小**约 7%。这份快照是 4 组 / 340 条 / 145.8 GB。

- **总览**：打开即见全貌——一行一个分组（体积 / 可回收 / 条目数），点任意一行进入对应分组。它是现算的合成视图，不占扫描器、不进缓存。
- **Git 仓库**（238 条 / 77.2 GB）：扫固定目录下的所有仓库，显示体积、最后提交、分支、脏文件、未推送提交，标出体积大的与久未动的。带构建产物的仓库（`node_modules` / `target` 等，白名单 + 项目标记文件判定）会在行上标「有产物」并单独记账——这些是可再生的，清掉它们保住源码，往往比删整个仓库更高频。
- **工具链缓存**（35 条 / 36.7 GB，其中 **9.5 GB 可清理**）：包管理器与语言运行时的缓存目录，加版本管理器的逐版本清单（本机 9 个 Node 版本）。
- **编辑器与 AI 工具**（59 条 / 23.3 GB，其中 **11.2 GB 可清理**）：VS Code 的用户数据与扩展、JetBrains 的配置与缓存，加 10 个 AI 编码工具的数据目录。

  十个 AI 工具的目录命名毫无共性——同一个东西 WorkBuddy 叫 `logs`，opencode 叫 `log`。所以不按工具建模，而是抽一层语义类别：日志、会话、缓存、技能、索引、配置、运行时、未知。**分类决定可清理性，工具只作归属标签**，筛选「可清理」就能跨工具一次看全。编辑器那半同口径：扩展与已装工具不可回收，日志 / GPUCache / 索引缓存算可回收。
- **本地模型**（8 条 / 8.6 GB）：Ollama / LM Studio / HuggingFace 三处的模型清单。
- **WSL 发行版**（只在 Windows 上出现）：每个 WSL2 发行版在宿主上就是一个 `ext4.vhdx`，读它的大小就知道这块盘被吃了多少。位置从注册表 `HKCU\...\Lxss` 拿——`wsl --list -v` 只给 NAME/STATE/VERSION 不给路径，而 vhdx 可能落在三种位置之一，只有注册表能全覆盖。

Java 环境与 iOS / Android / 鸿蒙的扫描器在仓库里但**暂时不进侧栏**；Docker 与 SSH 两组已实现但未注册。**总览的总占用因此是有意报不满的**。

## 口径

这几条不是实现细节，是界面上每个数字的含义：

- **体积是占用空间，不是逻辑大小**。删掉一个目录实际能回收的正好是占用空间：APFS/HFS+ 上压缩、副本（clone）、稀疏文件都会让逻辑大小显著偏离实际占用，用逻辑大小会把「可回收」报虚。Unix 上与 `du` 同源（`st_blocks × 512`）。
- **硬链接在单趟遍历内按 (dev, inode) 去重**（cargo `target` 这类硬链接密集目录不去重会虚高好几倍）。去重范围只限单趟：跨条目共享的硬链接（pnpm store 与项目 `node_modules` 共享同一批文件）各算各的，所以行加总可能大于全局唯一字节数。Windows 没有稳定的文件索引，维持不去重。
- **「可清理」= 点下去真能删掉**，不是「删了按需重下」。所以有官方清理命令的缓存（npm / pnpm / uv / pip / Homebrew / Go / Deno / NuGet / Composer 等）**一概不标可清理**，命令写在每行的「清理方式」里由你自己跑——`pnpm store prune` 只删没被引用的包，比搬走整个目录精确得多。代价是这几组的可回收数字明显小于目录实际占用。
- **版本管理器逐版本成行，且一律不可回收**。合成一行只会得到一句「2.8 GB」，真正有用的是「9 个 Node 版本里 v22.19.0 一个占 1.7 GB，最旧的 v12.18.0 还占 0.08 GB」。能不能卸取决于哪些项目在用它，本工具不读项目文件，报一个数会让人照着删掉还在用的版本。想知道哪个版本能卸，用各家自己的 `uninstall` 命令（写在每行的「说明」里）。
- **模型是资产不是缓存**。删一个要重新下载几十 GB，所以本地模型组**永不标可回收**，台账价值在「装了哪些模型、各占多少」。Ollama 的模型清单在 `manifests/`，权重本体是全模型共享的 `blobs/` 池，所以一个模型占多少 = 它 manifest 引用的 blob 占用之和；权重文件缺失时只计磁盘上有的部分，缺失层数写在明细里——照 manifest 里的 size 报会报出幻影。同一模型装了多个 tag 时共享层在各行各计一次（「这个模型攒出来要多大」的口径），「删掉单个 tag 实际腾出多少」看明细里的「共享层」一行。LM Studio 只扫 `models/` 与 `hub/models/`，HuggingFace 按模型目录整体计（`snapshots/` 是指向 `blobs/` 的软链，不重复计）。
- **WSL 的数字照实报，但不标可回收**。`ext4.vhdx` 动态扩展、只涨不缩：在发行版里删文件只在虚拟盘内部留空洞，Windows 侧文件尺寸纹丝不动。要把空间还给 Windows 得三步——发行版内 `sudo fstrim -av` → `wsl --shutdown` → 管理员执行 `Optimize-VHD -Mode Full`。本工具一条都不做，步骤写在界面里。这里回答的是「Linux 里明明删干净了，C 盘怎么还是满」，不是「点一下能清多少」。

## 安全边界

- **不接触任何凭据**：不读私钥、不进 `~/.ssh`。
- **AI 工具目录只读文件名，不读任何文件内容**。凭据藏在哪根本枚举不完——`auth.json`、`config.toml`、`settings.json` 里都可能写着 key；逐个文件做内容过滤是堵不完的漏洞，不读内容则从根本上消除了这条路径：凭据压根不进入数据流，不是「读出来再抹掉」。唯一的破例是 Ollama 的 manifest JSON（本地模型组）：它是层清单（digest + size + mediaType），不含凭据，而不读它就无法知道一个模型引用哪些权重 blob——blob 按 sha256 命名，文件名里没有任何模型信息。工具链组同样只走文件名与元数据。
- **扫描走白名单**，只在已知路径里扫，不 glob `~/.*` 或整个 `~/Library/Caches`——那下面还住着结构相似的敏感目录，以及性质不同的应用缓存。
- **WSL 只读注册表与文件元数据**，不执行任何 wsl 命令，也不进入发行版内部。
- **只揭示位置，不打开任何东西**。「在访达中显示」与「复制路径」不写盘、不执行任何程序；刻意不做「打开」——打开一个路径会执行它（`.app` / `.command` / 安装包）。不是宿主机路径的条目不出现这两个动作。
- **清理是唯一的写盘动作，只开三组**。这三组的「可清理」行能发起：检查器里点「清理」→ 弹窗列明将移入废纸篓的路径与字节数 → 确认才执行。三道闸：前端显式确认、服务端 `confirmed` 字段校验（缺字段直接拒）、`trash::delete` 移入废纸篓（绝不硬删，可从废纸篓恢复）。服务端**不信任前端传来的条目 id**，一律回白名单重查。仓库组内有两种动作，复核分两条：整仓删除查未推送提交与未提交改动（点下去到执行之间状态可能变，有则拒）；**清理构建产物查白名单、不查 git 状态**（产物可再生，不动源码与 `.git`，藏有 `.git` 的产物目录整目录拒）。AI 工具组按「工具 × 类别」复核：点击那一刻重读目录、按文件名重新分类，只删当前仍属日志 / 会话 / 缓存的直接子项。**会话含完整对话记录与代码片段，删除后不会自动重建**，弹窗单独说明。其余分组仍然只读。
- **不代跑用户级工具的命令**。代跑意味着新增「执行用户级子进程」这类能力，一旦开口子，「打开路径执行」「代跑 git」都只是同一个滑坡的不同位置。
- **不监听端口**，不是 HTTP 服务，没有跨域攻击面。这是选 Tauri 而不是 Web 的主要原因。

## 扫描策略

**默认吃缓存，启动时不扫描。**

1. 有缓存 → 直接返回，窗口毫秒级有内容，**不做任何后台扫描**
2. 无缓存（首次运行）→ 扫一次，否则没有数据可显示
3. 之后只有点「重扫」才真扫

早先的版本是「先出缓存 + 后台自动重扫」，刻意去掉了：数据变化极慢（本机两百多个仓库里近 7 天有提交的只有个位数），新扫的结果和缓存几乎一样，却让每次打开都在后台啃几十秒磁盘。页头一直显示「数据更新于 X 小时前」，要不要刷新交给人判断。

作者机器（4 组 / 340 条）全量扫描实测 **28.8 秒**（debug 构建的 `cargo run --example dump`，2026-10-20；release 更快）。瓶颈全在目录体积统计——用原生遍历（`scan/dirsize.rs`），不 shell 出 `du`。两个体积统计密集的分组并行跑只能收回一部分时间（并发会在 APFS 元数据层互相排队），所以「每加一个重分组，重扫就变慢」没有并行能兜底。

缓存带 schema 版本号，写入用临时文件 + rename 原子替换。**下面三种情况都要 +1**：

- **字段变更或增删 Scanner**——启动是「有缓存直接返回」，版本不变的话老用户拿到缺分组的旧快照，界面上没有任何提示让他点「重扫」，新功能等于白做。
- **扫描范围变了**——结构没动但扫哪些目录变了，缓存里存的是按旧范围扫出来的快照。
- **数字的口径变了**——同一棵树算出来的数字变了，老缓存里的数字跟新口径不可比，不跳版本的话「数据更新于」会让人误以为数字没变。

## 开发

```bash
npm install
npm run tauri dev
```

验证分三档，改什么就跑什么，红不往下走：

```bash
npm run verify:quick   # 内环：fmt + clippy + 类型检查 + 文档门禁，秒级，改完就跑
npm run verify         # 外环：内环 + 测试 + 构建，提交前
npm run verify:full    # 评估档：外环 + 全量扫描契约校验
```

导出扫描结果为 JSON（用于核对数据是否合理）：

```bash
cd src-tauri && cargo run --example dump | less
```

跑测试（只读本机真实数据，不做任何写入）：

```bash
cd src-tauri && cargo test
```

数据契约与前端约束见 [AGENTS.md](./AGENTS.md)。

## 结构

```
src-tauri/src/scan/
├── mod.rs             Scanner trait + 数据契约
├── repos.rs           Git 仓库扫描（含共用的体积遍历入口）
├── ai_tools.rs        编辑器与 AI 工具数据目录扫描
├── dev_env.rs         Java 环境 + iOS/Android/鸿蒙 探测型扫描（当前不进侧栏）
├── toolchain.rs       包管理器与工具链缓存扫描
├── local_models.rs    本地模型扫描
├── wsl.rs             WSL 发行版虚拟磁盘扫描（仅 Windows 注册）
├── ssh.rs             SSH 密钥扫描（已实现，未注册）
├── docker.rs          Docker 镜像与卷扫描（已实现，未注册）
└── tests.rs           集成测试
```

新增资产类型只需实现 `Scanner` trait 并注册进 `lib.rs::scanners()`，前端不用改——但要遵守三条前端约束：`fields` 最多三个（`Assets.vue` 只渲染 `slice(0, 3)`）、`detail` 是 HashMap 顺序不确定所以键名要前缀编号、分节与筛选读 `Item.group_key`（给了它名字就要以 `key · ` 开头）。

`examples/dump.rs` 走 `scanners()` 而不是另写一份列表，避免示例扫出来的分组和 app 里的对不上。

`src-tauri/src/roots.rs` 只做一件事：给出「Git 仓库」的扫描根目录。**这组根目录不可配置**，固定从 `~/Documents/Code`、`~/Projects`、`~/Developer`、`~/code`、`~/src`、`~/workspace` 六个常见位置往下找（存在的才扫）。

## 已知限制

- 体积统计走原生遍历，是全量扫描唯一的瓶颈。个别超大目录会触发**真超时**（60 秒，每层递归都查截止），该条目体积显示为 `—`。
- **AI 工具的分类靠目录名匹配**，覆盖率约六成。未识别的一律归入「未知」且不开放清理，所以漏识别的代价只是少显示一块可回收空间，不会误删。
- AI 工具各类别体积之和与工具根目录的整体实测值口径不完全一致（前者是各一级条目分别统计后相加，后者是一次整体遍历），允许少量出入（2% + 4 MB 容差）。
- **数据不会自动刷新**。这是刻意的，但意味着看到的可能是几天前的快照，靠页头的时间戳判断。
- 嵌套仓库的父仓库体积已扣除子仓库，但父子关系用 `Path::starts_with` 判断，跨盘的嵌套不会被识别。
- **「Git 仓库」的扫描根目录是固定的六个候选名**，代码放在别的命名习惯下就扫不到；环境变量改过位置的目录一律认不出来（本工具不读环境变量）。
- **工具链缓存与 AI 工具都走白名单**，LarkShell、微信开发者工具这类应用缓存不在内。加新来源前先确认删除后果。
- **Windows 上不做硬链接去重**，`file_index` 未稳定：那里的体积数字只虚不高，不会显示成错的。
- **WSL 的体积不等于发行版里实际用了多少**，而且是只涨不缩的。WSL1 没有虚拟磁盘，体积显示为「—」。位置与体积的读取没在 Windows 实机上跑过（开发机是 macOS）。
- 上面这些数字是本机一次快照，不是承诺。重扫之后数字会变，量级不变——要看当前值就 `cargo run --example dump` 跑一次。
