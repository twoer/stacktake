# Stacktake

本机资产清点台账。看看自己机器上到底堆了什么。

## 安装

V1 首发版本 **0.1.0**（2026-10-15）。从 [GitHub Releases](https://github.com/twoer/stacktake/releases) 下载对应平台安装包：macOS 为 `Stacktake_0.1.0_aarch64.dmg`（Apple Silicon；Intel 与 Windows 的安装包将在对应平台构建后补发）。

启动后**首次运行会扫一次全机资产**（约 20~30 秒，见「扫描策略」），之后默认真接读缓存，只有点「重扫」才重新扫描。macOS 首次打开若提示无法验证开发者，右键 → 打开（未签名构建，后续可签发）。

## 做什么

> 下面出现的体积与条目数（「本机 238 项合计 76.5 GB」这类）是**作者机器的一次扫描快照**，用来说明界面上会看到什么，不是你机器上的预期值。数字随机器与取数日期变化。

- **总览**：打开即见全貌——一行一个分组（体积 / 可回收 / 条目数），按固定语义序（源码 → 开发环境 → 依赖缓存 → 工具数据 → 模型 → 虚拟机）。点任意一行进入对应分组。它是现算的合成视图，不占扫描器、不进缓存。
- **Git 仓库**：扫指定目录下的所有仓库，显示体积、最后提交、分支、脏文件、未推送提交。标出体积大的、久未动的。本机 238 项合计 76.5 GB（体积按占用空间计、硬链接同一次扫描里只计一次——不去重的话 cargo `target` 这类硬链接密集目录会虚高好几倍）。带构建产物的仓库（node_modules / target 等，白名单 + 项目标记文件判定）会在行上标「有产物」并单独记账，检查器明细里每个产物目录一行各自的体积——这些是可再生的，清掉它们保住源码，往往比删整个仓库更高频。
- **编辑器与 AI 工具**：VS Code（`~/.vscode` 扩展与用户数据）、JetBrains（配置与缓存，按产品+版本展开）与 9 个 AI 编码工具的数据目录，按「工具 × 语义类别」聚合。本机合计 25.1 GB，其中约 12.8 GB 属于日志、会话、缓存这类历史数据。

  九个 AI 工具的目录命名毫无共性——同一个东西 WorkBuddy 叫 `logs`，opencode 叫 `log`。所以不按工具建模，而是抽一层语义类别：日志、会话、缓存、技能、索引、配置、运行时、未知。分类决定可清理性，工具只作为归属标签，这样筛选「可清理」能跨工具一次看全。编辑器那半（G1 补上）同口径：扩展与已装工具不可回收（主动选择），日志 / GPUCache / 索引缓存算可回收。
- **本地模型**：Ollama（`~/.ollama/models`）、LM Studio（`~/.lmstudio`）、HuggingFace（`~/.cache/huggingface/hub`）三处的模型清单。本机 8 个模型合计 8.6 GB。

  这一组的口径和其它组相反：模型是**资产**不是缓存，删一个要重新下载（几十 GB 起步），所以**永不标可回收**，台账价值在「装了哪些模型、各占多少」。Ollama 的模型清单在 `manifests/`（一个模型一个层清单 JSON），权重本体是全模型共享的 `blobs/` 池，所以一个模型占多少 = 它 manifest 引用的 blob 占用之和；权重文件缺失时只计磁盘上有的部分，缺失层数写在明细里（照 manifest 里的 size 报会报出幻影）。LM Studio 只扫 `models/` 与 `hub/models/`——`~/.lmstudio` 下的会话、日志与凭据目录不是模型资产，本工具不枚举。HuggingFace 按模型目录整体计（`snapshots/` 是指向 `blobs/` 的软链，不重复计）。

  同一模型装了多个 tag 时，Ollama 共享的权重层在各行**各计一次**（「这个模型攒出来要多大」的口径）——「删掉单个 tag 实际腾出多少」看明细的「共享层」一行（只在真有共享时出现；缺失层不进共享账）。「共享层」明细只在 Ollama 行出现：HuggingFace 的 blobs 池在每个模型目录内部、LM Studio 的权重是模型目录内的普通文件，行与行之间没有共享，行级体积已经是「删掉整行能腾出多少」的诚实口径。

  账上的 8.6 GB 与「三处目录合计约 9.2 GB」的直觉差在 LM Studio：那个目录实测 568 MB，但里面 **350 MB 是 `.internal/`（推理引擎二进制）、155 MB 是 `extensions/`**，没有一个字节是模型权重（`models/` 下 6 个目录全是空的，只有 `.DS_Store`）。这一组只认模型资产，引擎和扩展报进来是归类错误。
- **Java 环境**（**暂时隐藏**：2026-10-20 起不进侧栏；扫描器与测试原样保留，清空 `lib.rs::HIDDEN_GROUPS` 即恢复）：Maven 仓库、Gradle、JDK。本机 23 项合计 2.5 GB。

  Maven 按**二级 groupId** 拆分（`org/apache` 371 MB、`org/springframework` 213 MB…），取体积最大的 15 个，其余汇总成「其它 N 项」。粒度是量出来的：一级只有 47 个但 `org` 单独就 907 MB，看不出是谁占的；三级上千个，表格装不下。
- **iOS / Android / 鸿蒙**：探测型——**环境没装就整个分组不出现**，侧栏不留空 tab。鸿蒙另与 Java 一同**暂时隐藏**（2026-10-20），装了也不显示。

  三个都探测 IDE 本体与数据目录（`/Applications/Xcode*`、`~/Library/Android/sdk/*`、`~/.hvigor`、`~/.ohpm` 等）。本机没装 Xcode 与 Android SDK，所以这两组不显示；鸿蒙装过 DevEco Studio（扫出 4 项约 18.9 MB），但该组已暂时隐藏。
- **工具链缓存**：npm / pnpm / uv / pip / Homebrew / Rust / Go / Playwright / Electron 等 27 个目录（本机装了的 27 个里 **23 个是缓存**、4 个是已装工具链或二进制），加上 7 类版本管理器的逐版本清单（本机只有 nvm，9 个版本）。本机合计 36.3 GB——本机最大的单组，其中 **9.5 GB 可清理**，其余归各自官方命令与已装工具链 / 版本清单（见下）。

  边界有两条：**纯下载/依赖缓存且没有官方清理命令的算可回收**（删了按需重新下载，功能无损，走废纸篓）；**有官方清理命令的不算**——npm / pnpm / uv / pip / Homebrew / Go / Deno / NuGet / Composer 等 14 条各自有官方命令（写在每行的「清理方式」里），搬走整个缓存目录虽然也安全，但下次要完整重建，而官方命令只动真正多余的部分（`pnpm store prune` 只删没被引用的包），所以那部分由你自己跑命令，不走这里的清理入口。**已安装的工具链与二进制不算**（Rustup 工具链、Cargo/Go 已装工具、pnpm 自带的 Node）——删了丢功能，留哪个版本是主动选择，与 JDK 同口径。

  这条「有官方命令就不算可回收」是为了让账面与实际对齐：账面报「可回收」就是点下去真能删掉，代价是 toolchain 的可回收数字**明显小于**目录实际占用的缓存大小。S3（2026-10-13）起本组开放了清理入口，可回收口径同步收窄到约 10 GB。

  版本管理器（nvm / fnm / volta / pyenv / conda / rbenv / asdf）与上面那些不同，**逐版本成行**而不合成一行：nvm 那一栏合成一行只会得到一句「3.1 GB」，而真正有用的是「9 个 Node 版本，v22.19.0 一个占 2.0 GB，v12.18.0 停了三年还占 81 MB」。全部不可回收——本工具读不到哪个项目正在用哪个版本，要读各仓库的 `.nvmrc` / `engines` 再逐个求交集，报一个数会让人照着删掉还在用的版本。想知道哪个版本能卸，用各家自己的 `uninstall` 命令（写在每行的「说明」里）。

  顺带补上一个原先漏掉的可回收项：nvm 下载的 `tar.xz` 暂存在 `~/.nvm/.cache`，装完就是残留（本机 167 MB），跟 `versions/` 下已装的版本是两回事，分开列。

  走白名单而不是 glob `~/Library/Caches/*`：那下面还住着 LarkShell、微信开发者工具这类应用缓存，性质不同，逐个确认边界前不收。与 Java 分组也刻意不重叠，`~/.m2` 和 `~/.gradle` 归那边，否则总量双计。

  白名单里还有一批**本机一条都不装**的（NuGet / Composer / Coursier / SwiftPM / CocoaPods / Deno），它们的价值按定义就在「装了而本机没装」的那些机器上——所以本机的行数不因为它们增加。这些路径全部来自各家官方文档，但**没有一条经过实机核对**，且用 `NUGET_PACKAGES` / `COMPOSER_HOME` / `COURSIER_CACHE` 这类环境变量改过位置就认不出来。
- **WSL 发行版**（只在 Windows 上出现）：每个 WSL2 发行版在宿主上就是一个 `ext4.vhdx`，读它的大小就知道这块盘被吃了多少。位置从注册表 `HKCU\...\Lxss` 拿——`wsl --list -v` 只给 NAME/STATE/VERSION 不给路径，而 vhdx 可能落在 `Packages\<包名>\LocalState`、`%LOCALAPPDATA%\wsl\<GUID>` 或 `wsl --import --location` 指到的任意盘，只有注册表能覆盖全部三种。

  这一组的数字**照实报，但不标可回收**——vhdx 动态扩展、只涨不缩：在发行版里删文件只在虚拟盘内部留空洞，Windows 侧文件尺寸纹丝不动。要把空间还给 Windows 得三步：发行版内 `sudo fstrim -av` → `wsl --shutdown` → 管理员执行 `Optimize-VHD -Mode Full`（或 diskpart 的 `compact vdisk`）。本工具一条都不做，步骤写在界面里。所以这里回答的是「Linux 里明明删干净了，C 盘怎么还是满」，而不是「点一下能清多少」。

- **设置**：清空缓存、立即重扫、检查更新都在这个页面（侧栏「设置」）。

  扫描根目录**不可配置**：「Git 仓库」固定从 `~/Documents/Code`、`~/Projects`、`~/Developer`、`~/code`、`~/src`、`~/workspace` 六个常见位置往下找（存在的才扫），落在这些命名习惯之外的代码目录扫不到。这里曾经可以自己配（设置页增删、落盘 `scan-config.json`），2026-10-19 删掉了——它只对「Git 仓库」一组生效，而设置页是手输文本框，漏掉的人得先知道自己该填什么。
### 不在 V1 里的两组

**SSH 密钥**与 **Docker** 两个分组刻意移出 V1，侧栏不会出现它们（代码还在仓库里，只是没注册）。

- Docker 那 10.5 GB 的数据目录是**已实测存在**的占用，不计入是一个已知的、有意接受的取舍：最近一次实测（2026-10-19，S4 收口，6 个扫描分组 / 367 条）账面总占用 149.1 GB，补上那 10.5 GB 约 159.6 GB，**覆盖约 93.4%**。
- SSH 在体积维度上永远兑现不了（5 项合计 0 B），它回答的是「哪几把钥匙没在用」，属凭据卫生，与这块台账的叙事无关。移出它的顺带好处是这个工具**不再接触任何凭据**。

## 安全边界

- **不接触任何凭据**。SSH 分组移出 V1 后，这个工具不读任何私钥、不进 `~/.ssh`。`ssh.rs` 仍在仓库里（未注册），它「只取公钥部分、不把私钥内容读成数据、不落缓存」的约束与对应的泄漏自检测试一并保留着——它们守的是「万一加回来」。严格说那句约束是「读头但不读内容」：判断文件是不是密钥要读前 64 字节、判断有没有加密要读前 512 字节，两次都只做子串判断，内容不出进程（细节见 `AGENTS.md` 硬约束 3）。
- **AI 工具目录只读文件名，不读任何文件内容**。凭据藏在哪根本枚举不完——`auth.json`、`config.toml`、`settings.json` 里都可能写着 key。逐个文件做内容过滤是堵不完的漏洞，不读内容则从根本上消除了这条路径：凭据压根不进入数据流，不是「读出来再抹掉」。这条由测试从源码层面守着（`ai_tools.rs` 里禁止出现文件读取调用，`toolchain.rs` / `dev_env.rs` 同样守着）。**唯一的破例是 Ollama 的 manifest JSON**（本地模型组）：它是层清单（digest + size + mediaType），不含凭据，而不读它就无法知道一个模型引用哪些权重 blob——blob 按 sha256 命名，文件名里没有任何模型信息。破例范围仅此一种文件，权重本体、LM Studio 的 `settings.json` / `manifest.json`、HuggingFace 的快照一律只读元数据。
- **AI 工具扫描走白名单**，只在已知的 10 个路径里扫，不 glob `~/.*`——否则会误伤 `.ssh`、`.aws` 这类结构相似的敏感目录。
- **WSL 只读注册表与文件元数据**。位置读自 `HKCU\...\Lxss`，体积读自 `ext4.vhdx` 的文件大小。不执行任何 wsl 命令，也不进入发行版内部。
- **只揭示位置，不打开任何东西**。「在访达中显示」与「复制路径」不写盘、不执行任何程序。刻意不做「打开」：打开一个路径会执行它（`.app` / `.command` / 安装包），与「不读文件内容」是同一条理由。不是宿主机路径的条目不出现这两个动作——`Item.path` 不保证都是宿主机路径（Docker 原先给的 `docker://<镜像名>` 就是虚拟机里的东西，没有可揭示的位置），这条守卫照旧保留。
- **清理是唯一的写盘动作，只此三家**（S2 开 Git 仓库组，S3 开工具链缓存组，均 2026-10-13；B1 于 2026-10-17 开编辑器与 AI 工具组；P2 起仓库组内另开「清理构建产物」这一动作，仍属仓库组）。这三组的「可清理」行能发起：检查器里点「清理」→ 弹窗列明将移入废纸篓的路径与字节数 → 确认才执行。三道闸：前端显式确认、服务端 `confirmed` 字段校验（缺字段直接拒）、`trash::delete` 移入废纸篓（绝不硬删，可从废纸篓恢复）。复核对象按动作分：整仓删除查未推送提交与未提交改动（点下去到执行之间状态可能变）；**清理构建产物查白名单、不查 git 状态**（产物可再生，不动源码与 `.git`，藏有 `.git` 的产物目录整目录拒）；缓存组查这条是否仍在可清理白名单内；**AI 工具组按「工具 × 类别」复核**——id 里的根必须命中本次扫描白名单，并在点击那一刻重读目录、按文件名重新分类，只删当前仍属于日志 / 会话 / 缓存的直接子项（软链跳过）。**会话含完整对话记录与代码片段，删除后不会自动重建**，确认弹窗单独说明。**服务端不信任前端传来的条目 id**——拿路径回白名单重查一遍，产物目录更是由服务端在点击那一刻按白名单现找，不在白名单或没有删除实现一律拒。其余分组仍然只读：它们的「可回收」是「删了按需重下」的口径，没有删除入口。
- **不代跑用户级工具的命令**（D11 / S3 拍板）。工具链缓存里有 14 条各自有官方清理命令（`pnpm store prune` / `npm cache clean --force` / `uv cache clean` / `brew cleanup` 等），它们**不标「可清理」**，命令写在每行的「清理方式」里由你自己跑。这条边界是刻意的：代跑意味着新增一类能力（执行用户级子进程），一旦开口子，后面的「打开路径执行」「代跑 git」都只是同一个滑坡的不同位置。代价是那部分账面不计入「可回收」——报不满比报虚好。
- **不监听端口**，不是 HTTP 服务，没有跨域攻击面。这是选 Tauri 而不是 Web 的主要原因。

## 扫描策略

**默认吃缓存，启动时不扫描。**

本机全量扫描实测**约 21~32 秒**（出处：`cargo run --example dump`，2026-10-13，debug 构建；release 更快）。首次测得时侧栏还是 7 个分组；同日复测（移出 SSH 与 Docker 之后是 5 组 / 339 条）为 26.3 秒——那两组一个 0 B、一个只有说明没有明细，对耗时不构成量级影响。G1 收口再测（5 组 / 349 条，ai_tools 并入编辑器数据后多了 10 条）两次分别为 24991 / 20695 ms。G2 收口再测（6 组 / 357 条，新增本地模型 8 条）两次分别为 29400 / 24930 ms；G3 收口再测（6 组 / 367 条）25606 ms；H6 收口再测（同样是 6 组 / 367 条）**31973 ms**——条目数一条没变而耗时涨了 6 秒，是这台机器当下的负载，不是分组变多了。**同一份数据在不同时间跑出 25~32 秒，所以这里给的是区间不是定值**；差异来自文件系统缓存冷热与机器负载。瓶颈全在目录体积统计——Git 仓库 237 个与工具链缓存 36 个条目最大；体积是用原生遍历算的（`scan/dirsize.rs`），不 shell 出 `du`。两个有出处的对照点：git 子进程 0.14 秒（每仓库 5 次）、读缓存 4~5 毫秒（这次 5 毫秒，约 6000 倍），都不是瓶颈。S4 收口再测（体积口径加了硬链接去重，同样 6 组 / 367 条）**29.2 秒**——多链接条目查重的代价，仍在同一区间。H14 收口再测（java 与鸿蒙暂时隐藏，4 组 / 340 条）**28.8 秒**——少两组 27 条而耗时仍在同一区间：大头从来是仓库与工具链缓存的体积统计，Java 的 2.5 GB 与鸿蒙的 18.9 MB 不是量级因素。

两个体积统计密集的分组并行跑只能收回一部分时间——实测并发会在 APFS 元数据层互相排队（pnpm store 单个目录原生遍历 2.6 秒，与仓库扫描并发时谁都快不起来）。所以「每加一个重分组，重扫就变慢」这件事没有并行能兜底，加分组前先想清楚值不值。

所以启动流程是：

1. 有缓存 → 直接返回，窗口毫秒级有内容，**不做任何后台扫描**
2. 无缓存（首次运行）→ 扫一次，否则没有数据可显示
3. 之后只有点「重扫」才真扫

早先的版本是「先出缓存 + 后台自动重扫」。去掉自动刷新是因为它换不来新鲜度——本机两百多个仓库里近 7 天有提交的只有个位数，新扫的结果和缓存几乎一样——却让每次打开都在后台啃几十秒磁盘。页头一直显示「数据更新于 X 小时前」，要不要刷新交给人判断。

缓存带 schema 版本号，**字段变更或增删 Scanner 时都要 +1**，旧缓存自动作废；写入用临时文件 + rename 原子替换。

增删 Scanner 也要 +1 是因为启动逻辑是「有缓存直接返回」：版本不变的话，老用户拿到的是缺分组的旧快照，界面上也没有任何提示告诉他该点「重扫」，新功能等于白做。版本 +1 让他走一次首扫，代价是一次性的。

**扫描范围变了也要 +1**。删掉可配置根目录（2026-10-19）就是这种情况：结构没动，但扫哪些目录变了，自定义过根目录的老用户缓存里存的是按旧范围扫出来的快照——界面会继续显示那些已经不在扫描范围里的仓库，且没有任何提示说明它们是旧的。

**数字的口径变了同样要 +1**。硬链接去重（S4）就是这种情况：结构与范围都没动，但同一棵树算出来的数字变了（去重后普遍变小）——老缓存里的数字按旧口径存的，跟新口径不可比，不跳版本的话「数据更新于」会让人误以为数字没变。

## 结构

```
src-tauri/src/scan/
├── mod.rs        Scanner trait + 数据契约
├── repos.rs      Git 仓库扫描（含共用的体积遍历入口）
├── ai_tools.rs   编辑器与 AI 工具数据目录扫描（VS Code / JetBrains + 9 个 AI 工具）
├── dev_env.rs    Java 环境 + iOS/Android/鸿蒙探测型扫描（java / 鸿蒙两组暂时隐藏，见 `lib.rs::HIDDEN_GROUPS`）
├── toolchain.rs  包管理器与工具链缓存扫描
├── local_models.rs  本地模型扫描（Ollama / LM Studio / HuggingFace，G2）
├── wsl.rs        WSL 发行版虚拟磁盘扫描（仅 Windows 注册）
├── ssh.rs        SSH 密钥扫描（已实现，未注册——不进 V1）
├── docker.rs     Docker 镜像与卷扫描（已实现，未注册——不进 V1）
└── tests.rs     集成测试
```

`ssh.rs` / `docker.rs` 保留在树里但**没注册进 `scanners()`**，所以侧栏不会有这两组；重新启用只是在 `lib.rs::scanners()` 里加回两行。

`src-tauri/src/roots.rs` 只有一件事：给出「Git 仓库」的扫描根目录（`default_roots()`，常见代码目录里存在的才收）。它原先叫 `config.rs`，装的是可配置的根目录（设置页增删 + 三个 command），2026-10-19 删掉后改名。真实扫描走 `scanners_with_roots(roots::default_roots())`；`scanners()` 是「就用默认根目录」的入口（`dump.rs` 与注册哨兵测试用），两者同源。

新增资产类型只需实现 `Scanner` trait 并注册进 `lib.rs::scanners()`，前端不用改——但要遵守三条前端约束：`fields` 最多三个（`Assets.vue` 只渲染 `slice(0, 3)`）、`detail` 是 HashMap 顺序不确定所以键名要前缀编号、分节与筛选读 `Item.group_key`（给了它名字就要以 `key · ` 开头；维度名在前端按分组声明，≥2 个取值才出筛选按钮）。

`examples/dump.rs` 走 `scanners()` 而不是另写一份列表，避免示例扫出来的分组和 app 里的对不上。

## 已知限制

- 体积统计走原生遍历（`scan/dirsize.rs`），是全量扫描唯一的瓶颈。个别超大目录会触发**真超时**（60 秒，每层递归都查截止），该条目体积显示为 `—`。
- **AI 工具的分类靠目录名匹配**，覆盖率约六成。未识别的一律归入「未知」且不开放清理，所以漏识别的代价只是少显示一块可回收空间，不会误删。规则可以后续迭代补。
- AI 工具各类别体积之和与工具根目录的整体实测值口径不完全一致（前者是各一级条目分别统计后相加，后者是一次整体遍历），允许少量出入；测试用 2% + 4 MB 的容差守着（`ai_tools_sizes_stay_within_root`）。
- AI 工具与编辑器数据都只扫白名单里的已知路径（10 个 AI 工具 dot-dir + VS Code 的 `~/.vscode` 与 `~/Library/Application Support/Code` + JetBrains 的配置与缓存），不 glob `~/Library/Application Support/` 整个目录——那下面还住着微信开发者工具、Espressif 这类边界没逐个确认的应用。
- **数据不会自动刷新**。这是刻意的（见「扫描策略」），但意味着看到的可能是几天前的快照，靠页头的时间戳判断。
- 嵌套仓库的父仓库体积已扣除子仓库，但父子关系用 `Path::starts_with` 判断，跨盘的嵌套不会被识别。
- **「Git 仓库」的扫描根目录是固定的六个候选名**（`~/Documents/Code`、`~/Projects`、`~/Developer`、`~/code`、`~/src`、`~/workspace`，存在的才扫），代码放在别的命名习惯下就扫不到。这里曾经可以由设置页配置，**2026-10-19 删掉了**——只对这一组生效，且入口是手输文本框，等于要求用户先知道答案。环境变量改过位置的目录一律认不出来（本工具不读环境变量）。
- **Docker 的体积口径有三套**，界面数字和 `docker system df` 对不上是正常的：`docker system df` 报的合计（共享层只算一次）、明细行的虚拟大小（共享层重复计算，各行之和偏大）、数据目录实际占用（还含虚拟机系统与日志，最大）。另外 docker 用 1000 进制单位，界面按二进制显示，数字会小一成左右。
- Docker 明细行解析靠 `docker system df -v` 的表格文本。列数不符预期的行会被跳过并在界面里报出行数，不会填错列——宁可少一行也不要给错数字。
- **iOS / Android / 鸿蒙没装时分组整个消失**，这是刻意的（不留空 tab），不是漏扫。探测位置写在 `dev_env.rs` 的 `locations` 里。反过来，iOS / Android 只要装过就会显示。**Java 与鸿蒙是另一回事**：两组自 2026-10-20 起**暂时隐藏**（`lib.rs::HIDDEN_GROUPS`），装了也不进侧栏——鸿蒙那 18.9 MB 的 DevEco Studio 残留、Java 的 2.5 GB 都在此列；扫描器代码保留，清空名单即恢复。
- Maven 明细只列体积最大的 15 个二级 groupId（本机共 215 个），其余汇总成「其它 N 项」。想看全量改 `dev_env.rs::MAVEN_TOP`，但表格会被几 MB 的长尾淹没。
- **WSL 的体积不等于发行版里实际用了多少，而且这个数拆不掉**：`ext4.vhdx` 只涨不缩，删文件只在虚拟盘内部留空洞。压缩要走 `fstrim` + `wsl --shutdown` + `Optimize-VHD` 三步，本工具不做，界面里写清了步骤。WSL1 没有虚拟磁盘，体积显示为「—」而不是 0。位置与体积的读取没在 Windows 实机上跑过（开发机是 macOS，CI 上也没装 WSL）。
- **Maven 缓存与 JDK 都不标可回收**，是判断不是遗漏：Maven 删了要联网重拉；多个 JDK 并存是主动选择（17 与 21 都是长期支持版），不是残留。只有 Gradle 旧分发版与守护日志算真正的残留。工具链缓存组的口径更宽（纯下载缓存算可回收），但**有官方清理命令的那些反而不算**——账面要等于「点下去真能删掉」，详见上面工具链那段的边界说明。
- **工具链缓存是白名单**，LarkShell、微信开发者工具、Espressif 这类应用缓存不在内。加新来源前先确认删除后果，别 glob 整个 `~/Library/Caches`。
- **容器段不做明细**。它的 COMMAND 列会被截断且含空格、STATUS 词数也不定，解析不可靠；而容器可写层一共才几十 MB，不值得为它冒填错列的险。容器数量与总大小在说明里给出。
- Docker 分组只标「未被任何容器引用」的条目为可回收，比 `docker system df` 报的 reclaimable 保守——停止的容器仍然引用着镜像，删掉镜像它就起不来了。
- **上面标着 Docker 的四条限制**（三套体积口径 / 明细行解析 / 容器段不做明细 / 可回收口径）对应的是**已移出 V1、保留在仓库里的 `docker.rs`**：界面上不再显示这组，这些说明留给将来改那个文件的人（比如重新注册）。
- **总占用是有意报不满的。** SSH 与 Docker 移出 V1 后（见「不在 V1 里的两组」），最近一次实测（2026-10-19，S4 收口，6 个扫描分组 / 367 条）账面总占用 149.1 GB，而补上 Docker Desktop 那 10.5 GB 约 159.6 GB，**覆盖约 93.4%**——那 10.5 GB 永久不在账上是**有意接受的取舍，不是待修 bug**。
- **上面这些体积数是本机一次快照，不是承诺。** 全部取自 `cargo run --example dump` 的实跑（README 里凡是带日期的体积 / 条目数都是这么来的）；重扫之后数字会变，量级不变。要看当前值就自己跑一次 dump。
