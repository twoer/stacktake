# 已知限制（逐条细节）

> 本文是 [AGENTS.md](../AGENTS.md)「已知限制」的完整细节版：AGENTS 只留结论与指针，**规则以 AGENTS 为准**。
> 这些都是**已知的，不是 bug**；改动对应模块前先读相关条目。带日期的数字是当时实测，不是现状承诺。

- **「Git 仓库」不会全盘搜索**：默认只探测 `~/Documents/Code`、`~/Projects`、`~/Developer`、`~/code`、`~/src`、`~/workspace`（存在的目录才收，一个都没有时兜底 `~/Documents`）。默认位置之外的仓库需在空状态点「补充目录」，或在设置「Git 仓库扫描目录」用系统选择器补充；只影响 Git 仓库，不改变其它分组。补充位置落盘 `repo-roots.json`，清空扫描缓存不移除配置；外置盘离线保留配置并显示不可用，移除只取消扫描、不删除文件。增删后有完整缓存时只重扫仓库组，无缓存才回退全量。**与已有扫描范围重叠的目录会被拒绝**（同一处或互为父子，判据 `roots.rs::overlap_of`，纯函数；Windows 上路径比较不分大小写，Unix 上分），拒绝时不静默剔除被覆盖的旧项——两次点击各改各的，不替用户改写配置；提示会把冲突的那一项写出来（默认目录不可移除，文案单独点明）。启动仍只读缓存，不会因配置变化后台扫描；配置已写入而扫描中断时，旧仓库结果隐藏，等待用户重扫。其它分组仍不识别环境变量改过的位置（`NVM_DIR` 等）。**遍历跳过隐藏目录**：`ignore::WalkBuilder::hidden(true)` 是「**忽略**隐藏项」（也是它的默认值），不是「含隐藏目录」——注释曾写反过，别照着旧注释读。Windows 上 `.git` 默认带 HIDDEN 属性（本机全树 13 个隐藏目录全是它），不进 `.git` 内部正好省时间；代价是仓库**目录自己**被设了隐藏属性就扫不到。
- **Windows 侧的路径大多「按惯例推出来」，2026-10-24 已在实机跑过一轮**（未见需登记的差异，且一次真实清理成功入废纸篓——trash 的 Windows 删除路径随之实机验证；ai_tools 的 14 个根目录更早于 2026-10-23 单独核对，决策记录见 `archive/decisions/d17.md`）。映射表有测试守着（`windows_cache_locations_are_pinned` 钉有把握的几条、`every_whitelisted_cache_rel_resolves_on_windows` 守新增别漏），但实机只验「那台机器装了的东西探没探到」，没装的工具依然只由测试钉住映射——**别把一次实机跑通读成全部条目已核实**。推错的后果是漏显示，不是错数。**「Windows CI 绿了」依旧不等于「Windows 路径核对过了」**——CI 守的是另一半：`#[cfg(not(unix))]` 分支有人编译过、Windows 特有语义差异有人抓。`win_rel` 里 npm / pnpm / uv / node-gyp / Yarn / Cypress / electron-builder / Deno 这些的位置来自各工具文档或惯例布局，**改动前先查官方文档**，别按 macOS 直觉改。
- AI 工具与编辑器数据的根目录是白名单（`ai_tools.rs` 的 `AI_SPECS` / `EDITOR_SPECS` / `READ_ONLY_SPECS`）。**别改成 glob `~/.*` 或 glob 整个 `~/Library/Application Support/`**——会误伤 `.ssh`/`.aws` 这类结构相似的敏感目录，或收进边界没确认的应用缓存。M1（2026-10-26）起 `AI_SPECS` 含面向一般用户补的一批：Trae CN（`.trae-cn`，国内版是另一个目录）、Qwen Code（`.qwen`，官方文档核过）、Kimi Code（`.kimi-code`，官方文档核过；旧版 `~/.kimi` 已归档，刻意不收）、CodeBuddy（`.codebuddy` / `.codebuddycn`）、Codeium（`.codeium`，Windsurf 引擎与索引的另一半）。后四类本机（macOS）目录在；Windows 侧按 dot-dir 惯例推导，**待实机核对**。M2（同日）再收 Copilot CLI（`.copilot`）、Droid（`.factory`，官方文档）、Crush（`.crush`，sessions 在内）、Antigravity（`.antigravity`）与 READ_ONLY 的 Zed（两栏出自官方 CLI 文档，对话在 SQLite 只统计）；goose 因 Windows 布局与 XDG 不同构暂缓，待「可清 + 两栏」表形拍板。进白名单的判据 = 装机量大到漏账可感知 × 路径核实过，维护节奏是季度对一轮生态普查（如 yetone/magpie 的收录），不追平清单。
- `READ_ONLY_SPECS` 补充 DeepSeek Harness、Warp、OpenClaw、ZCode、灵码、Qwen Agent、Claude 桌面版（M1，Electron 数据先只统计），以及 Qoder CLI / 桌面版 / IDE 的独立数据位置；其中 14 个 Windows 根目录已于 2026-10-23 实机核对，Claude 桌面版的 Windows 位置（`%APPDATA%\Claude`）按 Electron 惯例推导待实机核，**全部仅统计，不开放清理**。数据存在不代表程序仍安装（Qwen Agent 本机仅见偏好文件），不扫描安装目录、更新器或另选的工作区。macOS 已提供可确认的映射，但未实机验证；灵码本地数据、Qwen Agent、Qoder CLI、Qoder IDE 的 macOS 独立位置尚未核实，显式留空；Warp 本地配置已包含在 macOS 的 `.warp` 根中，不重复计。自定义状态目录、WSL 内部数据与其它发行渠道不在这一轮范围内。
- 嵌套仓库父子关系用 `Path::starts_with` 判断，跨盘嵌套识别不到。
- **构建产物白名单是 clean-dev-dirs 调研清单的保守子集**（P2，`repos.rs::ARTIFACT_RULES`）：每条目录名都要求兄弟位置有项目标记文件（`node_modules` 要 `package.json`、`bin`/`obj` 要 `*.csproj`、`build` 要 Gradle/Flutter/CMake/setuptools 标记），深度不限（monorepo 子包）。`vendor` 与 Ruby `vendor/bundle` **刻意不进表**（常被整个提交进仓库，删了不是「可再生」）；`.next` / `.turbo` 这类框架缓存也未收，要收先补钉死测试。记账在扫描时顺带完成（dirsize 的 noting 钩子，同一次遍历，不额外付一趟全树成本）。
- **国际化（Track I）的三条边界**（P2a，2026-10-25）：① **es / ja / zh-TW 是 AI 初稿**，母语审校排在 P3，别把「五份目录键数相等」读成「译文已核实」；② `translate()` 缺条目时**回显键名**——界面上出现 `data.xxx` 就是目录缺这条翻译（Rust 侧门禁 `every_displayed_key_has_a_translation_in_all_five_catalogs` 只钉后端下发过的键，前端手写键没人管）；③ **翻的是展示位，不是数据**：`Item.name`、仓库名、路径、发行版与模型名保持原样（它们是搜索与筛选的词表，翻译了才对不上）。另：`SCHEMA_VERSION` 随 Text 契约 +1，**升级后第一次启动必然重扫一次**，不是缓存坏了。
- **调外部命令前先想 PATH**：双击打开的 app 拿到的 PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`，Homebrew 的第三方 CLI 在 `/opt/homebrew/bin`——终端里找得到，打包后就找不到。第三方 CLI 要显式兜底候选路径。活着的范例：`wsl.rs::reg_exe()`（先 `%SystemRoot%\System32\reg.exe` 再退回裸名）与 `docker.rs::find_docker`（Scanner 已未注册，规矩照旧）。
- **体积统计走原生遍历，不 shell out 到 `du`**（Windows 没有 du）。实现在 `scan/dirsize.rs`，口径、超时语义与实测差异写在那个文件的模块注释里。要点别改错：**口径是「占用空间」（`st_blocks * 512`），不是逻辑大小**——删掉一个目录实际能回收的就是占用空间，逻辑大小会把「可回收」报虚（APFS 压缩与副本会让两者显著偏离）；Windows 暂退回逻辑大小 `file_size`，要精确需 `GetCompressedFileSizeW`，等有实机补。**硬链接按 (dev, inode) 去重（S4 / D14），去重范围是单趟遍历**（对 repos 即单仓库 / 单行）——曾经不去重，cargo `target`（硬链接密集）实测虚高 4.6 倍、整个 repos 组虚高 1.45 倍。跨**行**共享的硬链接（如 pnpm store 与项目 node_modules 共享同一批文件）各算各的，行加总可能大于全局唯一字节数，这是「按行记账」的口径，不是 bug；Windows 无稳定文件索引，不去重，数字只虚不高。
- 体积统计的超时**是真超时**（`dirsize::SIZE_TIMEOUT`，60 秒）：每层递归查截止时间，超了立刻返回 `None`，界面显示 `—`。
- **本地模型按引用计，不按文件大小计**（G2）：Ollama 的权重本体是全模型共享的 `blobs/` 池、按 sha256 命名（文件名里没有任何模型信息），只能读 `manifests/` 里的层清单（digest + size + mediaType，不含凭据——「不读文件内容」在整个项目里只在这里破例，因为不读它就算不出一个模型引用了哪些权重 blob）才知道引用了哪些 blob；一个模型占多少 = 它 manifest 引用的 blob 占用之和。权重文件缺失时只计磁盘上有的部分，缺失层数写在明细里——照 manifest 里的 size 报会报出幻影。同一模型装了多个 tag 时共享层在各行各计一次（「这个模型攒出来要多大」的口径），「删掉单个 tag 实际腾出多少」看明细里的「共享层」一行。LM Studio 只扫 `models/` 与 `hub/models/`，HuggingFace 按模型目录整体计（`snapshots/` 是指向 `blobs/` 的软链，不重复计）。
- AI 工具分类靠目录名匹配，覆盖率约六成；未识别的一律归「未知」且不开放清理，漏识别的代价只是少显示一块可回收。**清理也走同一套分类**（B1）：服务端在点击那一刻重新读目录，只删当前仍属于日志 / 会话 / 缓存的直接子项（软链跳过）；**会话含完整对话记录，删除后不会再生**。
- **总占用是有意报不满的**：SSH 与 Docker 移出 V1 后，Docker Desktop 的数据目录实测 10.5 GB **永久不在账上**（有意接受的取舍，不是待修 bug——别为「补齐」把 docker 分组加回来）。S4 收口实测（2026-10-19，6 组 / 367 条）账面 149.1 GB，补上约 159.6 GB（覆盖约 93.4%）。**这个数会随仓库自然增长**，凡写它的都要带取数日期。
- **可回收合计 S4 实测（2026-10-19）是 25.2 GB**（repos 2.9 + toolchain 9.5 + ai_tools 12.8）。S3 时代曾把这一合计从 42.77 GB 收紧到 21.95 GB（14 条有官方命令的缓存约 20.9 GB 改判不可回收）——**不是丢数据是口径收紧**。此后数字又随数据增长回到 25 GB 档，**「全机可回收合计只增不减」和「只减不增」都是错的预期**，口径与数据两头都会动它。（句中「14 条」为 S3 当时口径；当前源码 `toolchain.rs` 已合并为 6 条 / 20.95 GB，金额一致、条目因白名单合并减少——以该文件注释与 `toolchain_sources_resolve_from_home` 等守备测试为准。）
- 下面三条 Docker 口径对应保留但未注册的 `docker.rs`（改那个文件才用得上）：数据在 Linux 虚拟机内部，宿主统计看不到，只能问 `docker` 命令行——三套对不上的口径（`docker system df` 合计 / 明细虚拟大小 / 桌面端目录占用）都给出并在 notes 写明差异，别「统一」成一个数；明细靠解析 `docker system df -v` 表格文本（镜像行从左取三列、从右取四列，中间 CREATED 词数不定；列数不符跳过并计数；**不要解析容器段**——COMMAND 截断含空格、STATUS 词数不定）；可回收只标「未被任何容器引用」的条目，比官方 reclaimable 保守（停止的容器仍引用着镜像）。
- Maven 明细只列体积最大的 15 个二级 groupId，其余汇总成「其它 N 项」（`dev_env.rs::MAVEN_TOP` 可改，但表格会被几 MB 长尾淹没）。JDK 与 Maven 缓存**都不标可回收**，是判断不是遗漏。Gradle 分发版「保留最新」靠目录名主版本号判定，目录名不合规就退化成全部标可回收（目前没遇到）。
- **工具链缓存分组是白名单，不是 glob**：`~/Library/Caches` 下还有 LarkShell、微信开发者工具等应用缓存，性质不同，只认 `toolchain.rs::sources()` 列死的目录。**与 Java 分组刻意不重叠**（`~/.m2`、`~/.gradle` 归 Java，双计由 `toolchain_sources_resolve_from_home` 守着）。**可回收口径比 Java 宽**：后者删了要重下/重建且无官方命令，前者要么有官方清理命令、要么是「删了按需重下」的纯下载缓存；已装工具链与二进制（Rustup 工具链、Cargo/Go 已装工具、pnpm 的 Node）一律不算，改这个边界必须同步 `toolchain_installed_artifacts_are_not_cleanable`。清理命令写在每行 detail 的「清理方式」里，没有官方命令的统一显示「直接删除目录」。
- **WSL 分组报体积，但永不标可回收——这是口径本身，不是漏了**。`ext4.vhdx` 动态扩展且只涨不缩：发行版里删文件只留内部空洞，Windows 侧尺寸纹丝不动。真把空间还给 Windows 要三步（发行版内 `sudo fstrim -av` → `wsl --shutdown` → 管理员 `Optimize-VHD -Mode Full` 或 diskpart `compact vdisk`），**本工具一条都不做**。`reclaimable` 在这里没有诚实的填法：填 0 会让人以为「没什么可清的」，而 WSL 用户最常见的困惑恰是「Linux 里删干净了 C 盘怎么还是满」。机制与压缩步骤写在 `wsl.rs` 模块注释、分组 notes、每行 detail 三处，别改成一个「可回收」的数。
- **WSL 的位置读自注册表，不扫目录**：`wsl --list -v` 不给路径；vhdx 有三处落点，只有注册表 `HKCU\...\Lxss` 的 `BasePath` 覆盖全部三种。**那条 `reg query` 没在 Windows 实机上跑过**（本机 macOS，CI 也没装 WSL）——解析与注册逻辑有测试守着（喂样本、注入读取），命令本身没有。用户名为中文时 reg 按代码页（GBK）输出，走 `from_utf8_lossy`：解不出的 `BasePath` 探不到 vhdx，该行体积缺失，不会报成错数。WSL1 没有虚拟磁盘，体积显示为未知（不是 0——报 0 等于说它不占空间）。
- **差额台账只回答「较上次」一个问题**（L1 / D18 拍板 A）：缓存信封只留**上一版**基线（`prev`），每次写入把「当前」轮转成基线——全量重扫整体换新，单组重扫只换该组（其余组的「上次」不动），摘组把该组基线删干净。边界与后果：① **只记 `size` 为严格 Bytes 的条目**——repos 遍历超时行（`Text("—")`）与体积未知的行（WSL1 等）不参与差额，拿 0 兜底会把超时行显示成假负差额；前端 `lib/delta.ts` 用同一口径。② **新条目无基线不显示，消失条目的基线随轮转剪掉**——不会出现「对不上号的行显示 0」。③ **补充目录变更后的第一次仓库重扫没有 repos 基线**（`load` 在配置变更时清空 repos，`rotate(Refresh)` 对空旧当前不留基线）——跨扫描范围的对比从根上不做，该组差额要等下一次扫描才恢复。④ 新出现的分组（如装上 Ollama 后注册）在整机差额里按 0 基线计，如实显示为增长。⑤ 清缓存清空基线；`SCHEMA_VERSION` 升级后首次启动必然重扫，那一扫也没有基线——差额一栏空白是「无基线」的合法态，不是功能坏了。⑥ 差额为 0 时三处展示位（masthead / 检查器整组 / 行）都不渲染，界面与没有这行时一致。
